# 上线前安全与质量评估报告

更新时间：2026-11-06

## 1. 结论

当前版本适合继续进行**受控内网、小范围试运行**，不具备可对外宣称的安全认证，也不应在未完成 HTTPS、外部渗透测试和异机灾备前直接开放为正式公网服务。

本报告是项目内部工程评估，不等同于等保测评、第三方渗透测试或安全合规证明。自动化测试通过只能证明已覆盖场景符合预期，不能证明不存在未知漏洞。

## 2. 评估范围

- Django Web/PWA、REST API、账号与组合权限。
- PostgreSQL 数据一致性、核心申请审批和出入库竞态。
- Nginx、Gunicorn、systemd、备份、恢复和发布追溯。
- Excel 导入、二维码查询、离线待复核和钉钉通知边界。
- 不包含：微信小程序、互联网大规模容量、第三方黑盒渗透、标签打印机真机。

## 3. 当前安全控制

| 领域 | 已实现 | 当前判断 |
| --- | --- | --- |
| 认证 | Django Session、时效 API Token、登录账号/IP 限流、令牌轮换/撤销 | 内部试运行可用 |
| 会话 | HttpOnly Session；退出使用 POST；密码由 Django 哈希保存 | 允许同账号多设备，暂无设备会话管理 |
| 权限 | 默认登录、组合权限、审批与出库分权、财务字段隔离 | 自动化正反向测试已覆盖主要入口 |
| 输入 | ORM、CSRF、上传类型/大小检查、Excel 结构化解析 | 仍需外部 DAST/人工攻击测试 |
| 数据一致性 | `transaction.atomic`、PostgreSQL 行锁、唯一约束、幂等键 | 已有业务冒烟；新增真实并发专项 |
| 审计 | 操作日志、生命周期日志、安全事件只增不改 | 登录成功/失败/阻断/退出均匿名化记录 |
| 网络 | Nginx 入口；Gunicorn/数据库仅本机监听检查 | 内网 HTTP 可试用；公网必须 HTTPS |
| 密钥 | `.env` 外置、发布包排除密钥、权限检查 | 需定期轮换和现场复核 |
| 灾备 | 本机定时备份、校验、隔离恢复演练 | 缺少加密异机副本，是正式上线阻断项 |
| 供应链 | `pip check`；服务器脚本可选 `pip-audit` | 需在每次候选发布固定执行漏洞扫描 |

## 4. 并发与多账号结论

核心状态动作不是依靠页面按钮防重，而是由服务层事务、行锁、唯一约束和幂等键共同保护。PostgreSQL 专项测试覆盖：

1. 两名审批人同时处理同一申请，只允许一个成功。
2. 两张申请同时预约同一资产，只允许一个成功。
3. 两名仓管同时快速出库同一资产，只生成一条有效流水。
4. 两笔耗材出库竞争同一库存，不允许出现负库存或超卖。
5. 多进程同时累计登录失败次数，不允许丢计数。

普通资料编辑目前仍是“后提交覆盖先提交”。这不会绕过核心出入库状态锁，但两人同时修改资产备注、库位资料等基础字段时可能覆盖对方内容。正式试运行建议为资产校正、基础资料和采购单编辑增加 `updated_at` 版本校验，冲突时提示刷新并人工合并。

## 5. 同账号多地登录策略

当前同一账号可在多个浏览器或设备同时登录。**不建议全员强制单点登录**：仓管常见场景是电脑操作加手机扫码，严格互踢会增加现场中断，也不能替代权限和数据库并发控制。

建议方案：

- 普通申请人允许多设备。
- 管理员、审批和出库账号默认最多 2 个可信会话。
- 增加“登录设备”页面，展示最近时间、IP 摘要、浏览器，支持退出其他设备。
- 新设备登录和会话撤销写入安全审计；高风险账号可选“新登录使旧会话失效”。
- 禁止多人共用同一个仓管账号，审计责任必须落到个人。

该策略会改变现有登录行为，实施前需要产品确认。

## 6. 钉钉与微信边界

当前钉钉能力是单向通知：群机器人发送系统消息；配置企业内部应用和用户映射后可发送个人工作通知。群机器人 Webhook 本身不能安全地接收指令。

双向钉钉可行，但应采用企业内部应用，而不是解析群里的自由文本：

1. 使用稳定 HTTPS 回调地址，验证钉钉签名和时间戳。
2. 将钉钉 UserId 映射到系统账号，继续执行系统原有权限检查。
3. 使用互动卡片处理“同意、拒绝、确认收货”等有限动作；复杂申请跳转移动 Web/PWA。
4. 每个回调使用事件 ID 做幂等，所有动作写入操作审计。
5. 驳回原因、资产选择、归还差异等复杂输入不得通过模糊群聊文本自动落账。

普通微信群不提供适合该系统的安全双向机器人入口。若以后需要微信侧发起业务，应使用企业微信应用或重新启动小程序项目；当前小程序仍不进入开发清单。

## 7. 二维码扫描规则

当前实现符合“识别与业务校验分离”：

- 扫码阶段只解析身份并把物品加入本次清单。
- 已售、维修中、已借出等资产不会因为状态不匹配而被丢弃，会显示为“已加入待修正”。
- 保存草稿允许保留这些条目，便于换表单类型或现场核对。
- 正式提交或快速执行时，服务端依据表单类型、资产状态、预占、持有人和库存再次权威校验。

这样既保证连续扫码速度，也避免把规则复制到扫描器、页面和服务端三处。扫描接口仍返回状态摘要用于提示，但状态不作为“是否记录本次扫描”的条件。

## 9. 2026-11-06 实测记录

- 本机 Django 全量测试：364 项通过，5 项 PostgreSQL 专项按设计跳过。
- NUC 隔离 PostgreSQL 测试库：5 项竞态测试全部通过，用时 8.688 秒。
- 测试结束后 `test_warehouse` 已销毁，`warehouse_app` 已恢复为无 `CREATEDB` 权限。
- NUC 业务计数保持：资产 637、耗材配件 31、导入批次 2、申请 0、流水 0。
- NUC 安全巡检：0 个阻断项、1 个提醒项；提醒为未安装 `pip-audit`。
- Django `check --deploy` 的 4 条提醒均为当前 HTTP 模式缺少 HSTS/SSL Redirect/Secure Cookie，公网开放前必须清零。
- NUC 只读入口基线：`/health/` 与 `/login/` 共 200 次 GET，并发 8，200/200 成功，吞吐 57.02 请求/秒，P95 204.38 ms，P99 256.16 ms。
- 本机无法连接 PyPI，`pip-audit`/Bandit 安装因网络超时终止；因此依赖 CVE 扫描和 SAST 仍是未完成项。

只读基线未覆盖登录后资产列表、扫码查询、报表和写操作，也没有同步采集 CPU/内存/磁盘 IO，不能作为正式容量结论。

## 10. 可重复执行方法

```powershell
# 本机功能回归（SQLite，验证业务逻辑，不证明 PostgreSQL 锁）
cd backend
..\.venv\Scripts\python.exe manage.py check
..\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
..\.venv\Scripts\python.exe manage.py test

# PostgreSQL 隔离测试库并发专项
sudo bash deploy/ubuntu22/run-concurrency-tests.sh

# 只读 HTTP 基线，不会提交表单
python tools/read_only_load_test.py \
  --base-url http://192.168.23.41/ \
  --path /health/ --requests 200 --concurrency 8

# NUC 配置和暴露面巡检
sudo /usr/local/sbin/after-sales-warehouse-security-check
```

压测结果必须同时记录 NUC CPU、内存、磁盘 IO、PostgreSQL 连接数和 Gunicorn 错误日志。仅有平均响应时间不足以判定可上线，至少需要 P95、P99、错误率和吞吐量。
